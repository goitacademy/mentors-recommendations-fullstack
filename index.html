HTML/CSS

Семантична верстка, блокова модель, Flexbox, форми та адаптивний дизайн. 6 модулів практичних порад — від структури сторінки до Mobile First.

МОДУЛЬ 1

Основи HTML та семантичної верстки

Семантика, структура сторінки, зображення та охайність проєкту.

1. Логотип — це посилання, а не текст чи картинка

●ТИПОВА ПОМИЛКА

Логотип реалізований звичайним текстом або зображенням без посилання.

✓ЯК ПРАВИЛЬНО

Логотип у хедері та футері завжди реалізовуємо посиланням з текстовим контентом <a href="./index.html">WebStudio</a>.

2. Семантична структура сторінки — обов'язкова

●ТИПОВА ПОМИЛКА

Уся сторінка складається з набору div.

✓ЯК ПРАВИЛЬНО

На сторінці обов'язково повинні бути:

  • header
  • main
  • footer

Це базова структура будь-якого проєкту.

3. Тег <nav> використовуємо правильно

●ТИПОВА ПОМИЛКА

У nav розміщують логотип, телефон та email.

✓ЯК ПРАВИЛЬНО

У тег nav поміщаємо тільки навігаційне меню. Логотип та контакти розміщуються окремо.

4. Дотримуйтесь ієрархії заголовків

●ТИПОВА ПОМИЛКА

Пропускаються рівні заголовків або відсутні заголовки секцій.

✓ЯК ПРАВИЛЬНО

На сторінці використовуємо один <h1>. Для заголовків секцій використовуємо <h2>. Для вкладених елементів — <h3>. Навіть якщо заголовка немає на макеті, для секції його потрібно додати, а приховування буде виконуватись через CSS.

5. Кнопка — це кнопка

●ТИПОВА ПОМИЛКА

Напис Order Service реалізований посиланням або текстом.

✓ЯК ПРАВИЛЬНО

Якщо елемент виконує дію — використовуємо тег button з типом type="button".

6. Однотипні елементи групуємо у списки

●ТИПОВА ПОМИЛКА

Картки, посилання, переваги або учасники команди створені окремими блоками без списку.

✓ЯК ПРАВИЛЬНО

Якщо на сторінці є перелік однотипних елементів — групуємо їх списком ul.

7. Уважно працюйте із зображеннями

●ТИПОВА ПОМИЛКА

Зображення завантажені не з тих фреймів макета, мають неправильні пропорції або відрізняються від тих, що використовуються в дизайні.

✓ЯК ПРАВИЛЬНО

Перед експортом уважно перевіряйте, що завантажуєте саме ті зображення, які використані в макеті. Після додавання на сторінку порівняйте результат із дизайном та переконайтеся, що зображення відповідає оригіналу. Для кожного тегу img обов'язково задавайте атрибути розмірів (мінімум width), а також коректний опис у атрибуті alt. Не покладайтеся лише на візуальне враження — завжди звіряйтеся з макетом перед здачею роботи.

8. Не ускладнюйте розмітку зайвими тегами

●ТИПОВА ПОМИЛКА

Велика кількість вкладених div та span без необхідності.

✓ЯК ПРАВИЛЬНО

Використовуйте семантичні теги HTML. div і span додаємо лише тоді, коли без них дійсно неможливо обійтися.

9. Перевіряйте шляхи до ресурсів

●ТИПОВА ПОМИЛКА

Шлях до зображення вказаний неправильно.

✓ЯК ПРАВИЛЬНО

Відносні шляхи повинні починатися з ./, інакше зображення може не працювати на GitHub Pages.

10. Оформлення проєкту теж має значення

●ТИПОВА ПОМИЛКА

Файли мають випадкові назви, а код не відформатований.

✓ЯК ПРАВИЛЬНО
  • Використовуйте тільки англійські назви файлів та папок.
  • Не використовуйте пробіли.
  • Не використовуйте великі літери.
  • Форматуйте код через Prettier.
  • Видаляйте зайві коментарі та непотрібний код.
МОДУЛЬ 2

Вступ до CSS

Шрифти, базові стилі, класи, селектори та стилізація тексту.

1. Підключайте всі шрифти одним посиланням

●ТИПОВА ПОМИЛКА

Roboto та Raleway підключені окремими посиланнями або не підключені необхідні варіації товщини.

✓ЯК ПРАВИЛЬНО

Підключайте всі необхідні шрифти та їх вагу одним посиланням із Google Fonts.

2. Основні стилі виносьте в body

●ТИПОВА ПОМИЛКА

Властивості font-family, font-size та color дублюються для великої кількості елементів.

✓ЯК ПРАВИЛЬНО

Повторювані стилі задавайте для body, щоб інші елементи успадковували їх автоматично.

3. Використовуйте зрозумілі назви класів

●ТИПОВА ПОМИЛКА

Класи мають неочевидні назви або містять цифри, великі літери чи трансліт.

✓ЯК ПРАВИЛЬНО

Імена класів повинні бути зрозумілими іншому розробнику, складатися тільки з англійських слів у нижньому регістрі та розділятися дефісом.

4. Не створюйте надто складні селектори

●ТИПОВА ПОМИЛКА

Для стилізації використовуються довгі ланцюжки на кшталт .section .title .text.

✓ЯК ПРАВИЛЬНО

Якщо селектор стає занадто довгим, створіть окремий клас для елемента та працюйте через нього.

5. Hover і focus завжди працюють разом

●ТИПОВА ПОМИЛКА

Для інтерактивних елементів реалізовано тільки :hover.

✓ЯК ПРАВИЛЬНО

Для посилань і кнопок завжди задавайте стилі одночасно для :hover та :focus.

6. Уважно перевіряйте стилізацію тексту

●ТИПОВА ПОМИЛКА

Розмір шрифту, висота рядка, колір або жирність відрізняються від макета.

✓ЯК ПРАВИЛЬНО

Усі текстові характеристики повинні точно відповідати макету: font-size, font-weight, line-height, letter-spacing, color.

7. Не забувайте про кольори фону

●ТИПОВА ПОМИЛКА

Задано лише колір тексту, але відсутній фон секцій або карток.

✓ЯК ПРАВИЛЬНО

Перевіряйте макет та задавайте background-color усім елементам, для яких це передбачено дизайном.

8. Логотип у хедері та футері оформлюється по-різному

●ТИПОВА ПОМИЛКА

Однаковий колір другої частини логотипа в хедері та футері.

✓ЯК ПРАВИЛЬНО

Акцентована частина логотипа ("Web") оформлюється через тег span, а кольори другої частини логотипа повинні відповідати макету для кожного блоку окремо.

9. Не дублюйте браузерні значення за замовчуванням

●ТИПОВА ПОМИЛКА

У стилях масово додаються властивості на кшталт font-style: normal або font-weight: 400.

✓ЯК ПРАВИЛЬНО

Не задавайте властивості, які вже встановлені браузером за замовчуванням, якщо їх не потрібно перевизначати.

10. Не використовуйте позиціонування завчасно

●ТИПОВА ПОМИЛКА

У стилях присутні position, top, left, right, bottom, width або height, скопійовані з макета.

✓ЯК ПРАВИЛЬНО

У цьому домашньому завданні працюємо лише з текстом та кольорами. Властивості позиціонування та розмірів поки не використовуються.

11. Уважно працюйте із зображеннями

●ТИПОВА ПОМИЛКА

Зображення завантажені не з тих фреймів макета, мають неправильні пропорції або відрізняються від тих, що використовуються в дизайні.

✓ЯК ПРАВИЛЬНО

Перед експортом уважно перевіряйте, що завантажуєте саме ті зображення, які використані в макеті. Після додавання на сторінку порівняйте результат із дизайном та переконайтеся, що зображення відповідає оригіналу. Для кожного тегу img обов'язково задавайте атрибути розмірів (мінімум width), а також коректний опис у атрибуті alt. Не покладайтеся лише на візуальне враження — завжди звіряйтеся з макетом перед здачею роботи.

12. Не забувайте про структуру проєкту

●ТИПОВА ПОМИЛКА

Відсутня папка css, папка images або використані довільні назви файлів.

✓ЯК ПРАВИЛЬНО

У корені проєкту повинні бути папки css та images, а всі назви файлів і папок мають бути англійською мовою без пробілів та кирилиці.

13. Перевіряйте валідність HTML

●ТИПОВА ПОМИЛКА

У розмітці залишаються незакриті теги або порушена вкладеність елементів.

✓ЯК ПРАВИЛЬНО

Перед здачею роботи перевіряйте HTML через валідатор та виправляйте всі знайдені помилки.

14. Перед здачею дочекайтесь оновлення GitHub Pages

●ТИПОВА ПОМИЛКА

Робота відправляється на перевірку одразу після пушу, через що ментор бачить стару версію сторінки.

✓ЯК ПРАВИЛЬНО

Після останніх змін зачекайте кілька хвилин, поки GitHub Pages оновить опубліковану версію сайту, і лише після цього здавайте роботу на перевірку.

МОДУЛЬ 3

Блокова модель. Flexbox

Контейнери, відступи, Flexbox та відповідність макету.

1. Не забувайте підключати modern-normalize

●ТИПОВА ПОМИЛКА

Файл normalizer не підключений або підключений після власних стилів.

✓ЯК ПРАВИЛЬНО

Підключайте modern-normalize у тегу head перед файлом styles.css. Це забезпечить коректну роботу блочної моделі та однакове відображення елементів у браузерах.

2. Контейнер повинен бути в кожній секції

●ТИПОВА ПОМИЛКА

Контейнер використовується лише в окремих секціях або винесений за межі секції.

✓ЯК ПРАВИЛЬНО

Контент кожної секції, а також хедера та футера повинен бути обгорнутий у div.container.

3. Використовуйте один загальний клас container

●ТИПОВА ПОМИЛКА

Для різних секцій створюються окремі контейнери з різними назвами та параметрами.

✓ЯК ПРАВИЛЬНО

На всьому сайті використовується один клас .container, який відповідає за обмеження ширини та центрування контенту.

4. Обнуляйте стандартні відступи браузера

●ТИПОВА ПОМИЛКА

Залишаються дефолтні margin та padding у заголовків, абзаців або списків.

✓ЯК ПРАВИЛЬНО

Перед початком роботи обнуліть стандартні відступи для h1-h6, p та ul, а всі необхідні відступи задавайте явно відповідно до макета.

5. Не плутайте margin та padding

●ТИПОВА ПОМИЛКА

Для внутрішніх відступів використовується margin або навпаки.

✓ЯК ПРАВИЛЬНО

margin використовується для відступів між сусідніми елементами, а padding — для відступів між контентом і межами елемента.

6. Секції не повинні мати зовнішніх відступів

●ТИПОВА ПОМИЛКА

Відстань між секціями реалізована через margin.

✓ЯК ПРАВИЛЬНО

У макеті секції розташовані одна під одною без зовнішніх відступів. Вертикальні відступи реалізуються через верхній та нижній padding секції.

7. Flexbox використовуйте лише там, де він дійсно потрібен

●ТИПОВА ПОМИЛКА

Flexbox застосовується до всіх елементів сторінки без необхідності.

✓ЯК ПРАВИЛЬНО

Flexbox використовуйте для горизонтального розташування елементів: навігації, списків, карток та інших блоків, де це передбачено макетом.

8. Не задавайте фіксовану висоту елементам

●ТИПОВА ПОМИЛКА

Для секцій, карток або контейнерів використовується властивість height.

✓ЯК ПРАВИЛЬНО

Висота повинна визначатися контентом. Фіксовану висоту в цьому домашньому завданні використовувати не потрібно.

9. Висота хедера формується падінгами посилань

●ТИПОВА ПОМИЛКА

Висота хедера задається через властивість height.

✓ЯК ПРАВИЛЬНО

Висота хедера та навігаційних посилань формується за рахунок вертикальних padding.

10. Для прихованих заголовків використовуйте спеціальний патерн

●ТИПОВА ПОМИЛКА

Заголовок приховується через display: none.

✓ЯК ПРАВИЛЬНО

Для прихованих заголовків використовуйте патерн sr-only, який зберігає доступність контенту для допоміжних технологій.

11. Правильно розраховуйте ширину елементів списку

●ТИПОВА ПОМИЛКА

Ширина карток задається навмання або через фіксовані значення.

✓ЯК ПРАВИЛЬНО

Для елементів списків рекомендовано використовувати calc() та враховуйте кількість елементів і проміжків між ними.

12. Використовуйте gap або контрольовані відступи

●ТИПОВА ПОМИЛКА

Для розташування карток використовується тільки justify-content: space-between.

✓ЯК ПРАВИЛЬНО

Надійніше використовувати gap або явно задавати відступи за допомогою margin між елементами відповідно до макета.

13. Правильно оформлюйте зображення

●ТИПОВА ПОМИЛКА

Зображення залишаються рядковими елементами або виходять за межі контейнера.

✓ЯК ПРАВИЛЬНО

Для всіх тегів img задавайте:

  • display: block
  • max-width: 100%
  • height: auto

Це забезпечить коректне відображення зображень.

14. Нижню частину карток оформлюйте окремим контейнером

●ТИПОВА ПОМИЛКА

Текстовий контент карток розташований без внутрішніх відступів.

✓ЯК ПРАВИЛЬНО

Контент під зображенням доцільно обгорнути в окремий div та задати йому необхідні падінги.

15. Не забувайте про рамки карток

●ТИПОВА ПОМИЛКА

У картках секції Portfolio рамка відсутня або застосована до всієї картки.

✓ЯК ПРАВИЛЬНО

У секції Our Portfolio рамка повинна бути лише в нижній частині картки, у блока який обгортає текст, відповідно до макета.

16. Уважно перевіряйте відповідність макету

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

Hero-зображення масштабується ширше, ніж передбачено макетом.

✓ЯК ПРАВИЛЬНО

Фонове зображення повинно відповідати вимогам макета та не перевищувати свій оригінальний розмір.

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

Псевдоелементи в цьому завданні використовуються виключно для декоративного оформлення.

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

16. Використовуйте правильні параметри анімації

●ТИПОВА ПОМИЛКА

Модальні вікна, поля, чекбокси та доступність форм.

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

3. Модальне вікно центрується відносно бекдропа

●ТИПОВА ПОМИЛКА

Модальне вікно зміщене або центрується відносно сторінки.

✓ЯК ПРАВИЛЬНО

Модальне вікно повинно бути вирівняне по центру як по горизонталі, так і по вертикалі відносно бекдропа.

●ТИПОВА ПОМИЛКА

У деяких інпутів відсутній атрибут name або використовуються неінформативні значення.

✓ЯК ПРАВИЛЬНО

Кожне поле форми повинно мати описове значення атрибута name, яке пояснює його призначення.

●ТИПОВА ПОМИЛКА

Текстова підписка до поля реалізована звичайним текстом без зв'язку з інпутом.

✓ЯК ПРАВИЛЬНО

Для кожного поля створюйте окремий label та пов'язуйте його з інпутом через атрибути for та id.

6. Не вкладайте інпути всередину label без необхідності

●ТИПОВА ПОМИЛКА

Уся структура поля форми вкладена всередину тега label, що ускладнює позиціонування іконок.

✓ЯК ПРАВИЛЬНО

Рекомендовано розміщувати label та input окремо та пов'язувати їх через for та id.

7. Не забувайте про placeholder

●ТИПОВА ПОМИЛКА

У полях відсутній текст-підказка або він не відповідає макету.

✓ЯК ПРАВИЛЬНО

Якщо в макеті є підказка, додавайте атрибут placeholder та стилізуйте його відповідно до дизайну.

8. Кнопки відправлення повинні мати type="submit"

●ТИПОВА ПОМИЛКА

Кнопки форм використовують тип за замовчуванням або type="button".

✓ЯК ПРАВИЛЬНО

Для кнопок відправлення форми використовуйте type="submit".

9. Текст Subscribe не є заголовком

●ТИПОВА ПОМИЛКА

Текст "Subscribe" у футері оформлений через заголовок або входить до структури форми.

✓ЯК ПРАВИЛЬНО

Використовуйте тег p. Цей текст не повинен бути дочірнім елементом форми.

10. Форма підписки повинна відповідати макету

●ТИПОВА ПОМИЛКА

Форма у футері розташована без відступу від соц. мереж.

✓ЯК ПРАВИЛЬНО

Форма підписки повинна бути вирівняна відповідно до макета та розташовуватися біля правого краю контейнера.

11. Нові іконки додавайте до SVG-спрайту

●ТИПОВА ПОМИЛКА

Іконки форми підключаються окремими SVG-файлами.

✓ЯК ПРАВИЛЬНО

Усі нові іконки необхідно додавати до файлу icons.svg та використовувати через SVG-спрайт.

12. Правильно позиціонуйте іконки в інпутах

●ТИПОВА ПОМИЛКА

Іконка позиціонується відносно самого input або без контейнера.

✓ЯК ПРАВИЛЬНО

Інпут та іконка повинні знаходитись у спільному контейнері з position: relative, а сама іконка позиціонується через position: absolute.

13. При абсолютному позиціонуванні задавайте координати

●ТИПОВА ПОМИЛКА

Використовується position: absolute, але відсутні координати.

✓ЯК ПРАВИЛЬНО

Завжди задавайте необхідні координати (top, left, right, bottom) для передбачуваного розташування елемента.

●ТИПОВА ПОМИЛКА

Іконка зміщується вниз та не потрапляє точно в центр.

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

При фокусі змінюється лише рамка або лише іконка.

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

Перевірка роботи форми виконується лише мишкою.

✓ЯК ПРАВИЛЬНО

Перевірте навігацію через клавішу Tab та роботу чекбокса через Space.

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

Серверний компонент відповідає за prefetch, а вся клієнтська логіка повинна знаходитися в окремих файлах:

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

7. Уважно працюйте з env-змінними

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

Навігація створюється через звичайні HTML-посилання.

✓ЯК ПРАВИЛЬНО

Для внутрішньої навігації використовуйте компонент Link із Next.js. Це забезпечує коректну роботу маршрутизації та попереднє завантаження сторінок.

9. Не забувайте про loading.tsx та error.tsx

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

Slug обробляється як рядок.

✓ЯК ПРАВИЛЬНО

У маршруті [...slug] Next.js передає параметр як масив. Необхідно отримати тег зі значення slug та використовувати його:

  • під час SSR prefetch;
  • у клієнтському useQuery.

●ТИПОВА ПОМИЛКА

Фільтрація працює лише після перезавантаження сторінки.

✓ЯК ПРАВИЛЬНО

Tag повинен бути частиною queryKey та використовуватись під час виконання fetchNotes. Інакше React Query буде повертати старі дані з кешу.

✓ЯК ПРАВИЛЬНО

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

✓ЯК ПРАВИЛЬНО

●ТИПОВА ПОМИЛКА

●ТИПОВА ПОМИЛКА

Перевіряється тільки список нотаток.

✓ЯК ПРАВИЛЬНО

Структура проєкту, middleware, маршрути та обробка помилок на базовому Express-сервері.

●НА ЩО ЗВЕРНУТИ УВАГУ

Завдання потрібно виконувати в репозиторії nodejs-hw у гілці 01-express. Гілку main не потрібно видаляти або перейменовувати.

Перед початком роботи перевірте, що ви створили потрібну гілку та працюєте саме в ній. У LMS потрібно додати посилання на GitHub у форматі https://github.com/student/nodejs-hw/tree/01-express.

●НА ЩО ЗВЕРНУТИ УВАГУ

✓РЕКОМЕНДАЦІЯ

Не зберігайте основну логіку сервера в корені проєкту. У корені мають бути лише конфігураційні файли, наприклад package.json, .env, .gitignore, .prettierrc та конфігурація ESLint.

●НА ЩО ЗВЕРНУТИ УВАГУ

Сервер повинен запускатися на порті, який береться зі змінної оточення PORT. Якщо змінна не передана, потрібно використовувати порт 3000.

✓РЕКОМЕНДАЦІЯ

Створіть файл .env і додайте туди PORT=3000. У коді використовуйте dotenv, щоб підвантажити змінні оточення.

4. Обов'язково підключіть базові middleware

●НА ЩО ЗВЕРНУТИ УВАГУ

У цьому завданні сервер має використовувати стандартні middleware: cors, express.json() та pino-http.

✓РЕКОМЕНДАЦІЯ

Перевірте, що всі middleware підключені до реєстрації маршрутів або в правильному місці логіки сервера. cors дозволяє робити запити з інших доменів, express.json() дозволяє серверу читати JSON у body, а pino-http допомагає бачити вхідні HTTP-запити.

●НА ЩО ЗВЕРНУТИ УВАГУ

  • GET /notes;
  • GET /notes/:noteId;
  • GET /test-error.
✓РЕКОМЕНДАЦІЯ

Перевірте кожен маршрут вручну в браузері або через Postman. Для GET /notes сервер має повертати об'єкт з повідомленням Retrieved all notes. Для GET /notes/:noteId сервер має повертати повідомлення з переданим noteId.

✓РЕКОМЕНДАЦІЯ

7. Додайте глобальний обробник помилок

●НА ЩО ЗВЕРНУТИ УВАГУ

✓РЕКОМЕНДАЦІЯ

●НА ЩО ЗВЕРНУТИ УВАГУ

✓РЕКОМЕНДАЦІЯ

9. Перевірте деплой на Render

●НА ЩО ЗВЕРНУТИ УВАГУ

Потрібно надати не тільки посилання на GitHub, а й посилання на задеплоєний проєкт на render.com.

✓РЕКОМЕНДАЦІЯ

Після деплою обов'язково відкрийте задеплоєний бекенд і перевірте всі маршрути. Особливо перевірте:

  • /notes;
  • /notes/:noteId;
  • /test-error;
  • будь-який неіснуючий маршрут для перевірки 404.

10. Перед здачею перевірте проєкт повністю

●НА ЩО ЗВЕРНУТИ УВАГУ

Перевірте, що у проєкті підключено middleware для читання cookies. Без цього req.cookies буде недоступним, і маршрути refresh, logout та authenticate не працюватимуть коректно.

14. Реалізуйте middleware authenticate

●НА ЩО ЗВЕРНУТИ УВАГУ

Усі маршрути нотаток мають бути доступні тільки авторизованому користувачу.

✓РЕКОМЕНДАЦІЯ

Створіть файл src/middleware/authenticate.js. Middleware має:

  • перевіряти наявність accessToken;
  • шукати сесію в базі;
  • перевіряти термін дії access token;
  • знаходити користувача;
  • записувати користувача в req.user;
  • викликати next().

15. Закрийте всі маршрути нотаток авторизацією

●НА ЩО ЗВЕРНУТИ УВАГУ

Після додавання авторизації кожен користувач має бачити тільки свої нотатки.

✓РЕКОМЕНДАЦІЯ

Застосуйте authenticate до всіх маршрутів нотаток. Без авторизації маршрути нотаток не повинні працювати.

16. Додайте userId до моделі Note

●НА ЩО ЗВЕРНУТИ УВАГУ

✓РЕКОМЕНДАЦІЯ

17. Оновіть контролери нотаток

●НА ЩО ЗВЕРНУТИ УВАГУ

Після додавання авторизації не можна просто шукати всі нотатки або нотатку тільки за _id.

✓РЕКОМЕНДАЦІЯ

  • getAllNotes повертав тільки нотатки поточного користувача;
  • getNoteById шукав нотатку за _id і userId;
  • updateNote оновлював тільки нотатку поточного користувача;
  • deleteNote видаляв тільки нотатку поточного користувача.

Якщо нотатка не знайдена або належить іншому користувачу, потрібно повертати повідомлення Note not found.

18. Перед здачею перевірте всі auth-маршрути

●НА ЩО ЗВЕРНУТИ УВАГУ

✓РЕКОМЕНДАЦІЯ

●НА ЩО ЗВЕРНУТИ УВАГУ

✓РЕКОМЕНДАЦІЯ

●НА ЩО ЗВЕРНУТИ УВАГУ

5. Реалізуйте маршрут request-reset-email

●НА ЩО ЗВЕРНУТИ УВАГУ

✓РЕКОМЕНДАЦІЯ

Перевірте, що:
